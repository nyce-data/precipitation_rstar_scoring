# RRS: Repository resilience

## Repository resilience defined

Robustness of the hosting institution’s data infrastructure: governance stability, redundancy, backup arrangements, distributed replication, and track record through prior funding disruptions. Because higher resilience means lower risk, it enters the formula inverted. A score of 80 on RRS becomes a contribution of 4 to R*, correctly rewarding well-governed repositories while flagging fragile ones.

RRS covers each repository that holds a copy of the dataset, judged as an institution: its redundancy, integrity checks, disaster recovery, funding and track record. "For" means the repository is resilient. A repository serves the dataset in its original format with its metadata: the archive of record (the parent), its copies and mirrors (children) and the producer's own site count; volunteer snapshots and third-party reformatted copies don't. RRS gives one pooled verdict across all of them.

## Subcategories

### RRS-1

#### Description

Geographic redundancy

≥2 geographically independent sites hold verified copies

#### How to find

Find the data repository or location where the dataset is stored and being served. Looking for evidence of geographic redundancy that the data is stored in two different geographic places. Search for multiple data endpoints (mirrors, data repository(s), different organizations serving the same data).

#### What counts as evidence

Copies of the dataset held in at least two places that are geographically independent: mirrors, other data repositories, or other organizations serving the same data.

### RRS-2

#### Description

Regular backup integrity verification

Checksum checks quarterly or more frequently

#### How to find

Find the data repository or location where the dataset is stored and being served. Search for the data repository operations plan or a CoreTrustSeal plan. Search for a mention of dataset checksum checks.

#### What counts as evidence

A repository operations plan or certification (such as CoreTrustSeal) that describes checking the stored files against checksums, and how often that happens. Quarterly or more often meets the bar.

### RRS-3

#### Description

Disaster recovery plan tested

Tested within the past 2 years with documented results

#### How to find

Find the data repository or location where the dataset is stored and being served. Search for a data repository operations plan or a CoreTrustSeal plan that describes what they will do if there is an interruption of service, if they can't serve data for an extended period of time. Do they have a documented plan and do they have steps of how to implement it.

#### What counts as evidence

A documented disaster recovery plan for the repository, with the steps it would take if it could not serve data for a long time, and a record of the plan being tested in the past two years.

### RRS-4

#### Description

Stable institutional funding

No imminent political, budgetary, or administrative threat to operations

#### How to find

Find the data repository or location where the dataset is stored and being served. Search for threats in the news and any funding changes from 2025-present. Is there evidence the funding is sufficient or are there budget and funding cuts coming?

#### What counts as evidence

News and budget records from 2025 to the present on the repository's funding: whether it is enough to keep running, or whether cuts or other political or administrative threats are coming.

### RRS-5

#### Description

Track record through prior disruption

Repository has survived at least one major funding or leadership disruption without data loss

#### How to find

Find the data repository or location where the dataset is stored and being served. Search for a funding decrease or interruption, and then search the number of data holdings in the data repository before and after a funding decrease or interruption. Were there noticable changes such as delays in ingesting and serving datasets?

#### What counts as evidence

A past funding cut or leadership change at the repository and how it came through: whether any data were lost, and whether ingesting new datasets or serving existing ones slowed down afterwards.
